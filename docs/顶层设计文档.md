## 1. 项目概述

### 1.1 项目背景

当前钻井液相关业务数据存在大量人工录入场景。业务人员需从钻井液日报（PDF/TXT/图片）中获取数据，再按业务系统要求逐项填写。

**现有痛点**：
- 数据来源格式复杂：电子PDF、扫描件、图片、TXT混排文本并存
- 结构化数据（密度、井深）与非结构化描述（异常情况、处理措施）交织
- 同一字段在不同文档中名称不统一（"密度"/"泥浆密度"/"Density"）
- 人工填写重复性高，存在漏填、错填风险
- 内部业务系统已投入使用，无法修改原有网页

### 1.2 项目定位

> **在不改造现有业务系统的前提下，自动解析业务文档，将识别出的信息按照预定义业务规则映射到目标字段，并通过模拟人工操作完成网页填写。**

---

## 2. 建设目标

### 2.1 总体目标

实现完整闭环：

```
业务文档导入 → 文档内容解析 → 业务字段提取 → 人工确认 → 网页自动填写
```

### 2.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **轻量化** | 普通办公电脑可运行，不依赖云端服务 |
| **本地化** | 文档解析、数据处理全部本地完成，业务数据不外传 |
| **非侵入式** | 不修改业务系统，不要求增加接口 |
| **浏览器无关** | 不绑定特定浏览器，通过 Windows UI Automation 操作用户当前打开的业务页面 |
| **原文保真** | 长文本完整保留原始内容，不摘要、不改写 |
| **规则可配置** | 字段映射关系采用配置化设计，便于扩展 |
| **可追溯** | 每个填写字段可追溯到原始文档来源 |

## 4. 功能模块设计

### 4.1 文件输入模块

**职责**：接收业务人员提供的数据文件

**支持格式**：
- PDF（电子版优先，扫描件降级OCR）
- TXT（需分析排版结构，非简单字符串处理）
- JPG/JPEG/PNG（图片格式，走OCR流程）

**处理模式**：
- 第一版：单文件处理
- 后续扩展：批量处理队列

---

### 4.2 文档解析与识别模块

根据文件类型采用不同解析策略：

#### 电子PDF（优先路径，核心输入）

```
电子PDF → PyMuPDF → 文字 + 坐标 → 几何关系恢复（对齐/聚类/投影）→ Table / KeyValue / Paragraph
```

重点获取：
- 文字内容及其精确坐标
- 页码、文本块、行、词的空间关系
- 字体及版面信息

**不默认执行 OCR，也不依赖 OpenCV 做表格检测**——有文字层的 PDF 通过文本坐标的几何关系即可恢复表格结构。

> **转置表风险提示**：实际日报中的性能数据表为转置表（字段名在左列、取样点在顶行），标准行列检测算法默认字段名在首行，转置表会产出错误结构。表格恢复流程需增加"转置检测与翻转"子步骤，POC 阶段将此作为重点验证项。

#### 扫描PDF / 图片（降级路径）

```
扫描件/截图 → OpenCV 图像预处理（灰度、二值化、降噪）
           → 表格结构检测（边缘检测 + 轮廓发现 + 单元格分割）
           → ppocr_lite OCR 识别 → 文字 + 位置
```

OpenCV 与 OCR 仅在此路径使用：
1. **图像增强**：灰度化、自适应二值化、去噪，提升 OCR 识别率
2. **表格结构恢复**：通过边缘检测和轮廓分析定位表格区域，分割行列单元格

#### TXT文本

不简单按字符串处理，而是恢复二维排版结构：
- 分析换行、空格、缩进
- 识别字段与数值的对应关系
- 恢复表格型排版的空间关系

> **可行性提示**：TXT 无坐标信息，纯靠空格对齐的表格在不同编辑器/字体下差异大，解析难度可能不低于扫描件 OCR。POC 阶段需单独验证"空格对齐的 TXT 能否稳定解析"，若验证不通过，MVP 中降低此格式优先级。

---

### 4.3 版面结构恢复模块

**这是系统的核心能力之一**。

不直接将原始文档映射到网页，而是先恢复文档的逻辑结构。

**表格恢复区分两条路径**：

```text
路径A（电子PDF，主路径）：
  文本坐标 → 行对齐聚类 → 列边界投影 → 转置检测与翻转 → Table
  （纯几何关系计算，无 OCR、无 OpenCV）

路径B（扫描件/截图，降级路径）：
  OpenCV 表格检测 → 单元格分割 → OCR 逐格识别 → 转置检测与翻转 → Table
  （Canny 边缘检测 + 轮廓发现 + 投影/连通域分析）
```

**转置表处理**：检测到表格首列为文本型字段名、首行为数值型取样点时，判定为转置表并自动翻转行列，使字段名回到首行的标准结构。此步骤对两条路径均适用。

```
Document
├── Header        (页眉、标题)
├── KeyValue      (键值对：井号: XX-001)
├── Table         (表格数据)
├── Paragraph     (段落文本)
├── Section       (章节)
└── Other         (其他)
```

**示例**：

```
原文："井号：ABC12-3-4"
→ KeyValue { field: "井号", value: "ABC12-3-4" }

原文："密度   黏度   API失水
       1.18   48     6.2"
→ Table { rows: [...] }

原文："现场循环过程中发现返出黏度升高，现场加入降黏剂处理后恢复正常。"
→ Paragraph { text: "..." }
```

### 4.4 业务字段映射模块

建立统一的业务字段模型，解耦文档字段名与内部业务字段：

```
文档字段名        →    业务字段ID       →    网页目标字段

"泥浆密度"            density              input[name='density']
"Density"             density              input[name='density']
```

**映射机制**：
- 领域词典：收录常见字段别名
- 规则配置：YAML/JSON定义字段对应关系
- 类型转换：自动处理单位、格式差异

### 4.5 数据校验与人工确认模块

**设计理念**：第一版不追求完全无人值守，默认采用人机协同模式。

```
AI/规则识别 → 人工检查 → 自动填写 → 人工最终确认
```

**低置信度处理**：
- 识别不确定的字段标记为异常
- 强制人工修正，不强行填写
- 后续可对高置信度数据开放自动确认模式

### 4.6 网页自动填写模块

**前提条件**：业务人员已完成登录并进入目标页面

模块内部明确拆分为两个独立子层：

#### 定位器（Locator）

只负责"找到目标控件"，输出统一的定位结果（控件句柄/坐标/焦点路径），不执行任何写入动作。

```
输入：字段描述符（label文本、AutomationId、控件类型）
策略（分层降级，架构全预留、按需实现）：
    1. UI Automation 控件属性匹配（通过 Name/ClassName/AutomationId 直接命中）
    2. 辅助文字定位（UIA Name 属性为空时，通过相邻 StaticText 控件的文本内容推断目标控件）
    3. 视觉区域定位（UIA 信息不完整时，对页面截图做 OCR 定位控件位置，POC 验证后决定是否启用）
    4. 键盘 Tab 导航推断（按 Tab 键顺序遍历焦点，记录控件序列后按位置推断目标）
    5. 屏幕坐标估算（兜底，基于页面布局的相对位置估算坐标）
输出：LocatorResult { handle, bbox, method, confidence }
```

#### 操作器（Actor）

只负责"对已定位的控件执行动作"，接收定位器的输出，不关心控件是怎么找到的。

```
输入：LocatorResult + 待写入值
动作：SetValue / SendKeys / 下拉选择 / 多行文本逐行输入 / 焦点校验
输出：操作结果 + 回读校验（重新读取控件值与期望值比对）
```

**拆分收益**：
- 定位策略可独立升级（如后续加入视觉定位），不影响操作逻辑
- 失败可精确定位环节：定位失败 ≠ 写入失败，日志与重试策略分别处理
- 同一定位结果可用于「填写前预览高亮」和「填写后回读校验」

**整体流程**：
```
工具检查当前窗口 → Locator 逐字段定位 → 预览定位结果
→ Actor 逐字段写入 → 回读校验 → 汇总报告
```

**安全约束**：
- 不自动触发提交按钮
- 全局急停快捷键（Esc）
- 填写前校验活动窗口标题/进程名

## 5. 核心数据结构

### 5.1 Business Data Model（业务数据中间层）

系统在「文档解析」与「网页填写」之间引入一个明确的中间数据模型，实现两侧彻底解耦：

```
文档解析层                业务数据中间层              网页填写层
(Document Layer)   →    (Business Data Model)   →   (Page Layer)
输出：逻辑结构块          输出：标准化业务实体         输入：字段定位+操作指令
```

**中间层定义**（JSON Schema 示例）：

```json
{
  "report_type": "drilling_fluid_daily",
  "meta": {
    "well_name":       {"raw_text": "ABC12-3-4", "confidence": 0.98},
    "date":            {"raw_text": "2020/3/26", "normalized": "2020-03-26", "confidence": 0.97}
  },
  "fluid_properties": [
    {"sample_point": "#1", "density": {"raw_text": "1.18", "value": 1.18, "unit": "g/cm³"},
     "funnel_viscosity": {"raw_text": "48", "value": 48, "unit": "s"}}
  ],
  "materials_consumed": [...],
  "narrative": {
    "engineering_summary": {"raw_text": "...原文...", "source_bbox": [...]},
    "treatment_log":       {"raw_text": "...原文...", "source_bbox": [...]}
  }
}
```

**设计要点**：
- 中间层是**唯一的数据交换契约**：解析层只管产出中间层，填写层只消费中间层
- 每个业务值都携带溯源信息（source、confidence），随中间层一起流转
- 新增日报模板 = 新增一份解析规则；新增录入页面 = 新增一份页面映射配置；两者互不影响
- 中间层可序列化为 JSON 存档，便于问题排查与审计

### 5.2 字段溯源模型

每个目标字段存储完整的溯源信息：

```yaml
raw_text: "1.18"              # 原始提取文本，录入默认使用
normalized_value: 1.18         # 标准化值，用于逻辑判断
unit: "g/cm³"                 # 单位
confidence: 0.95               # 置信度
source:
  file: "钻井液日报.pdf"
  page: 1
  bbox: [112, 384, 518, 426]   # 原始坐标
```

### 5.3 原文保真机制

系统将原始文本与标准化文本分离存储：

- **raw_text**：原始识别结果，用于最终填写网页
- **normalized_text**：用于规则匹配、字段识别，可进行格式标准化

**最终网页录入默认使用 raw_text**，确保不因语义理解而修改业务人员原始描述。

**硬性规则**：

> **自然语言字段禁止语义改写；结构化字段允许必要的格式标准化。**

即："工程作业简况""钻井液处理与维护"等段落文本必须原样录入（不摘要、不改写、不润色）；而密度、日期、数量等结构化数据仅允许单位换算、日期格式统一等必要标准化，且 raw_text 始终保留。

## 7. 技术路线（初步建议，POC后锁定）

### 7.1 技术选型方向

| 模块 | 选型 | 备注 |
|------|------|------|
| 桌面端GUI | **tkinter** | Python 自带，零额外依赖，打包体积最小 |
| PDF解析 | **PyMuPDF** | 直接提取文字层+坐标，性能优 |
| OCR | **ppocr_lite**（ONNX Runtime） | PP-OCR 系列 ONNX 模型，无需 PaddlePaddle 框架，依赖仅 numpy + Pillow + onnxruntime |
| 图像预处理 + 表格结构恢复 | **OpenCV** | 扫描件增强 + 表格区域检测（边缘检测、轮廓发现、单元格分割） |
| 网页自动化 | pywinauto / Windows UI Automation | 模拟人工操作，不绑定浏览器 |
| 配置管理 | **PyYAML** | 字段映射规则配置 |
| 数据交换 | 本地 JSON | 轻量级 |
| 打包分发 | **PyInstaller** | 打包为单目录 exe，无需目标机器安装 Python |

### 7.2 技术选型原则

- **成熟优先**：选择有稳定社区支持的方案
- **轻量优先**：避免引入重型框架（如大型Agent框架、RAG系统）
- **按需加载**：OCR等重资源模块仅在需要时加载
- **离线可用**：核心功能不依赖互联网

### 7.3 大模型定位

**第一版不将大模型作为核心依赖**。

对于无法通过规则解决的复杂字段识别，可在后续版本增加可选的本地或内部模型能力。

## 8. 自动填写对接方案（初步）

### 8.1 页面接入策略

**方案：Windows UI Automation（系统级控件访问）**

```
业务人员打开浏览器 → 登录系统 → 进入目标页面
        ↓
工具通过 Windows UI Automation 枚举当前窗口控件树
        ↓
根据控件属性（Name/ClassName/AutomationId）定位目标输入框
        ↓
执行填写操作（SetValue / SendKeys / Select）
```

**优势**：
- **浏览器无关**：不依赖 CDP/Selenium，Chrome、Edge、Firefox 均可
- **不修改业务系统**：不注入 JS，不安装扩展
- **复用用户已有登录态**：工具不接触登录流程
- **系统级能力**：Windows 原生 API，稳定性高

**降级策略（架构全预留，POC 验证 UIA 覆盖度后决定实现范围）**：
- 第一层：UI Automation 控件属性定位
- 第二层：页面文字/OCR 定位
- 第三层：视觉区域定位
- 第四层：键盘 Tab 导航 + 焦点定位
- 第五层：鼠标坐标操作（兜底）

### 8.2 安全防错机制

- **前置窗口校验**：检查当前活动窗口标题/进程名是否匹配目标系统
- **非破坏性原则**：仅执行输入和选择，不触发提交按钮
- **全局急停**：Esc 立即终止所有自动操作

## 9. 打包与分发策略

### 9.1 目标

将工具打包为 **Windows exe 可执行文件**，拷贝到目标机器即可运行，不要求安装 Python 环境。

### 9.2 打包方案

使用 **PyInstaller** 打包为单目录模式（onedir）：

```
项目代码 + 依赖库 + OCR 模型文件 + ONNX Runtime DLL
    ↓ PyInstaller
    ↓
dist/
└── 钻井液日报工具/
    ├── 钻井液日报工具.exe
    ├── _internal/         # 依赖库、模型、DLL
    └── config/            # 字段映射规则等配置
```

### 9.3 体积目标

**目标：控制在普通办公电脑可接受的部署体积。** 主要体积构成为 Python 运行时、onnxruntime、OpenCV 及 OCR 模型文件；具体数字以 POC 打包测试结果为准，实测后回填本节。

### 9.4 打包注意事项

- OCR 模型文件需显式打包进 `_internal/` 目录，运行时不依赖网络下载
- onnxruntime 的 CPU 推理 DLL 需包含（不需要 GPU 支持）
- 配置文件（`field_rules.yaml` 等）放在 exe 同级目录，便于用户修改
- 首次运行时自动检测并初始化模型路径

### 10.3 高 DPI 兼容

Windows 高分屏（如 2560×1600 + 150% 缩放）下，UIA 返回逻辑像素坐标，pyautogui 使用物理像素坐标，两者偏差 = DPI 缩放比（1.5x）。解决方案：

```python
import ctypes
ctypes.windll.shcore.SetProcessDpiAwareness(1)  # 在 tkinter/UIA 导入前设置
```

设置后 UIA 和 pyautogui 统一使用物理像素，坐标一致。此调用必须在任何 UI 库导入之前执行。

## 14. MVP范围（第一阶段）

### 14.1 目标

选定 **1种典型钻井液日报 + 1个实际业务录入页面**，完成完整闭环验证。

### 14.2 覆盖字段

**结构化字段**：
- 井号、日期、井深、钻井液类型
- 密度、黏度、AV/PV/YP、API失水等性能参数
- 至少3-5种材料消耗数据

**长文本字段**：
- 工程作业简况
- 钻井液处理与维护

**UI控件类型**：
- 普通文本输入框
- 多行文本框（长文本）
- 下拉选项
- 表格型数据（动态增行）

### 14.3 验证目标

MVP需验证三个关键问题：

1. **文档结构能否稳定恢复** — PDF解析的准确性和鲁棒性
2. **业务字段能否准确对应** — 规则映射的正确率
3. **网页操作是否可靠** — 不同浏览器下的兼容性

### 14.4 POC 优先级

**POC 不直接开发完整软件**，优先用最小代价消除两个最大的不确定性：

```text
POC-1：真实 report_data.pdf 能否稳定恢复业务数据
        （PyMuPDF 提取 → 几何关系表格恢复 → 字段映射，脚本级验证即可）

POC-2：真实业务网页能否通过 Windows UI Automation 定位并填写
        （输入框、下拉框、多行文本框各至少一个，脚本级验证即可）
```

两者跑通后，GUI、配置化、打包均属确定性工程问题，可并行推进。

## 16. 核心设计思想

```
文档解析与网页填写解耦
规则优先，模型辅助
原文优先，不改变业务描述
不改业务系统，模拟业务人员原有操作
```
